# kmdBlog システム設計

最終確認日: 2026-10-29

この文書は、現行コード・テスト・設定から復元したシステム設計です。将来案を現行要件として扱わないため、次のラベルを使用します。

- **確認済み**: 現行コード、テスト、設定、またはマイグレーションで確認できる事実
- **推定**: 実装から読み取れるが、採用理由や要件として明文化されていない事項
- **提案**: 今後の変更候補。承認済み要件ではない
- **未決定**: 選択肢があり、判断が必要な事項

## 1. システムの目的と範囲

### 確認済み

kmdBlog は次の機能を持つブログアプリケーションです。

- 公開済み記事の一覧・検索・詳細表示
- 作品一覧・詳細表示、プロフィール、規約等の公開ページ
- Google OAuth と招待によるユーザー登録
- 管理画面での記事作成・更新・削除、画像アップロード
- 管理者による招待、ロール変更、ユーザー有効・無効化
- 公開記事の sitemap、robots、OGP 等の生成

管理対象はアプリケーションコードと Cloudflare 用設定です。Cloudflare リソースの作成、シークレット登録、各環境へのデプロイはリポジトリ外の運用です。

## 2. コンテキストと実行基盤

```text
閲覧者 / 編集者 / 管理者
          |
          v
Next.js App Router on Cloudflare Workers
  |       |         |          |
  |       |         |          +--> Resend API（招待メール）
  |       |         +-------------> Google OAuth
  |       +-----------------------> R2（Markdown、画像）
  +-------------------------------> D1（ユーザー、招待、記事メタデータ、タグ）
```

### 確認済み

- Next.js を `@opennextjs/cloudflare` で Worker 形式にビルドし、Wrangler で実行・デプロイします。
- `dev`、`stg`、`prod` は別の Wrangler 設定と Cloudflare リソースを持ちます。
- `main` への push は GitHub Actions からステージングへ自動デプロイされます。
- 本番デプロイは npm スクリプトにはありますが、GitHub Actions にはありません。

### 未決定

- Issue #4でVinextへの段階移行を採用しました。devのログイン・記事・画像表示とstg環境を所有者が確認済みです。切戻し実機検証は管理者承認で省略しました。stgのCI設定はVinextへ変更済み（実行未確認）で、本番はOpenNextを維持しています。[切替条件と手順](migrations/vinext-phase-4-production.md)を参照してください。
- 環境ごとの `compatibility_date` をいつ、どの検証後に揃えるかは標準化されていません。現行設定には環境差があります。

## 3. アプリケーション境界

| 領域 | 主な場所 | 責務 |
| --- | --- | --- |
| 公開 UI | `app/(public)` | 公開済み記事・作品・固定ページの表示 |
| 認証 UI | `app/(auth)` | ログインと招待受諾 |
| 管理 UI | `app/(private)` | 記事、プロフィール、ユーザーの管理 |
| 認証 | `auth.ts`、`proxy.ts` | Google OAuth、JWT セッション、管理ルートの入口制御 |
| 書き込み処理 | `lib/actions` | Server Actions による投稿・画像・ユーザー操作 |
| データアクセス | `lib/db.ts`、`lib/posts.ts`、`lib/users.ts` | D1 への読み書き |
| オブジェクト保存 | `lib/r2.ts` | Markdown と画像の R2 読み書き |
| Markdown 表示 | `lib/markdown` | Markdown のレンダリングと表示部品 |
| 入力検証 | `validations`、`lib/images` | Zod と画像内容判定による入力制約 |
| 画像配信 | `app/media/[...key]/route.ts` | R2 画像の同一オリジン配信とキャッシュ制御 |

公開・認証・管理の route group は URL を分ける目的ではなく、レイアウトとメタデータを整理する単位です。管理画面のアクセス制御は `proxy.ts` と各 Server Action / Server Component の両方に存在します。

## 4. データ設計

### D1

| テーブル | 主な責務 | 主な制約 |
| --- | --- | --- |
| `users` | OAuth ユーザー、ロール、有効状態、プロフィール | email と Google subject が一意 |
| `invites` | 招待トークン、対象 email、付与ロール、期限、使用日時 | token が一意 |
| `posts` | 記事メタデータ、公開日時、R2 キー | slug が一意、author は削除制限 |
| `tags` | タグ名 | name が一意 |
| `posts_tags` | 記事とタグの多対多関係 | post/tag の組が一意 |

### R2

- `R2_POSTS`: 記事本文を Markdown として保存します。D1 の `posts.r2Key` がオブジェクトを参照します。
- `R2_IMAGES`: 検証済み画像を、元ファイル名を使わない UUID ベースのキーで保存します。

### 推定された設計意図

D1 を検索・関連・公開状態の管理に使い、大きな本文と画像を R2 に分離することで、構造化問い合わせとオブジェクト保存の責務を分けています。この理由は現行構成と過去の作業記録には整合しますが、正式な採用判断の記録はありません。

## 5. 主要フロー

### 5.1 サインインと招待

1. Google OAuth から email とプロフィールを受け取ります。
2. 既存ユーザーは `isActive` が true の場合だけサインインできます。
3. 未登録の `OWNER_EMAIL` は初回管理者として作成されます。
4. それ以外の未登録ユーザーは、未使用かつ期限内の招待が email と一致すると作成されます。
5. セッションは JWT 方式で、ユーザー ID、ロール、有効状態を格納します。

**確認済み:** 管理者だけが招待を作成でき、招待メールは Resend API から送信されます。

**既知の注意点:** 招待 email には一意制約がなく、招待の確認・ユーザー作成・使用済み更新は単一トランザクションではありません。同時実行時の採用ルールは未定義です。

### 5.2 管理画面へのアクセス

1. `proxy.ts` が `/management` 以下で認証済みユーザーの存在を確認します。
2. `/management/admin` 以下では `admin` ロールを要求します。
3. Server Components と Server Actions も、処理に応じてセッションとロールを確認します。
4. 画像アップロードはセッションだけでなく D1 の最新ロールと有効状態を再確認し、確認に失敗した場合は拒否します。

**確認済み:** 入口の proxy は未認証をログインへリダイレクトし、非管理者の admin ルートを 403 にします。

**既知の注意点:** 投稿やユーザー操作の Server Actions は認可方法が統一されておらず、画像アップロードだけが共通ヘルパーで D1 を再確認します。停止済みユーザーや変更直後のロールを全操作で確実に拒否する契約は、現時点では統一されていません。

### 5.3 記事の作成・更新・削除

- 作成: 入力検証後、R2 に Markdown を保存し、D1 に記事とタグ関係を保存します。
- 更新: 対象記事を確認し、R2 本文、D1 メタデータ、タグ関係を順に更新します。
- 削除: D1 のタグ関係と記事を削除し、R2 本文は復旧余地を残す目的で保持します。
- 公開: `publishedAt` が設定され、現在時刻以前の記事だけを公開系クエリが返します。

**確認済み:** admin と editor は記事を作成できます。削除は admin または記事の作成者に限定されています。一方、更新の Server Action には所有者確認がなく、editor も他のユーザーの記事を更新できます。

**既知の注意点:** D1 と R2 をまたぐトランザクションはありません。途中失敗により、R2 の孤立オブジェクト、本文とメタデータの不一致、タグの部分更新が生じる可能性があります。補償処理、再試行、定期清掃の方針は未決定です。

### 5.4 画像アップロードと配信

- admin または editor かつ D1 上で有効なユーザーだけがアップロードできます。
- slug、空ファイル、5 MiB 上限を検証します。
- JPEG、PNG、WebP の実データを magic bytes で判定し、申告された MIME type を信用しません。
- UUID キーと条件付き PUT により、元ファイル名の混入と意図しない上書きを避けます。
- `/media/*` は拡張子から固定した `Content-Type`、`nosniff`、CSP、同一オリジン制約、ETag と Cache-Control を付与します。

この境界はテストで明示されています。

## 6. 横断的な設計

### 認証・認可

- 認証は Google OAuth、セッションは最大 7 日の JWT です。
- ロールは `admin`、`editor`、`author`、`reader` の4種です。
- 現在、投稿編集権限を持つのは `admin` と `editor` です。
- 現在 admin ロールのユーザーに対するロール変更・停止は Server Action で禁止されています。
- proxy は補助的な入口制御です。機密操作の最終認可は必ずサーバー処理側で行う必要があります。

### 入力・出力の安全性

- 記事とプロフィールは Zod で長さ・形式を検証します。
- 新規記事の slug は小文字英数字とハイフンに制限します。
- 画像は内容判定、サイズ制限、安全なキー、固定レスポンスヘッダーを使用します。
- Markdown レンダラーは `rehype-sanitize` を選択可能ですが、既定値は無効です。現構成では raw HTML 用プラグインを使用していません。将来 raw HTML を有効化する場合は、sanitize を必須条件として再設計する必要があります。

### 同時実行・重複

- D1 の一意制約が email、slug、token、tag、記事タグ組の重複を最終的に防ぎます。
- 画像は UUID と R2 の `etagDoesNotMatch: "*"` で上書きを防ぎます。
- slug の事前確認後にも一意制約競合は起こり得ます。利用者向けエラーへの変換は一部未実装です。

### 障害・再試行

- メール送信は失敗時に最大3回、指数バックオフで試行します。現行実装は 429、5xx、ネットワークエラー以外も catch 節で再試行します。
- 画像の認可確認と保存失敗は fail-closed とし、利用者には詳細を伏せたエラーを返します。
- 記事作成・更新では、D1/R2 の部分失敗から自動回復する仕組みがありません。

### 監査・可観測性

- アプリケーションログは一部の失敗を `console.error` / `console.warn` に記録します。
- `/api/health` は稼働状態と `APP_ENV` を返します。
- 誰がいつロール、ユーザー状態、記事、招待を変更したかを保持する監査ログはありません。
- ログの保持期間、アラート、相関 ID、個人情報のマスキング基準は未定義です。
